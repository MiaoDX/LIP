端侧模型的
评测体系

云端评测通常围绕服务化模型能力，端侧评测还必须覆盖“最终交付到设备上的那个东西”。同一份权重换个芯片、换个量化方案、换个内存预算，表现就不一样。我过去几年做的正是这件事：在有限端侧资源里定义指标、建立准出、把验收做成可以连续跑的流水线，只是被测对象从感知模型换成了语言与多模态模型。

端侧团队特有的评测问题

  • 评测对象是部署后的产物，指标里天然带着延迟、内存、功耗和量化损失
  • “能力密度”这类技术叙事，需要跨代际、跨尺寸可比的能力度量作为地基
  • 文本、多模态、语音多条模型线，需要共用一套评测基础设施而不是各做各的
  • 评测要同时服务内部迭代信号、开源社区可信度、客户验收和对外榜单
01 / Positioning

评测的瓶颈
通常不在指标学，在 harness

我关心的是：怎样让能力、资源约束、证据和准出进入同一套可复现、可无人值守连续运行的评测体系
Object

评测的是交付物，不是权重

端侧模型真正被用户使用的形态，是经过量化、编译、芯片适配之后的产物。评测口径如果停在权重层，跨芯片一致性、量化退化和资源超限都会滞后到集成期才暴露。

Metric

指标要从下游任务倒推

公开 benchmark 是必要但远不充分的。真正决定下游成败的维度，往往不在榜单里，需要从实际使用它的那个环节反推出来，再补进评测集。

Harness

从人工盯屏到自动准出

把人脑里的验收判断拆成 metric、证据、报告和门禁，评测才能从“发版前突击跑一轮”变成每个 checkpoint 都在跑的常态化基础设施。

02 / Evidence

四段和评测直接相关的经历

Case A · VLN Evaluation

具身导航模型：当标准指标不足以判断任务成败

去年团队开始做 VLN 模型，我主要负责数据与评测两块。评测跑的是 Habitat / VLNCE 这类标准 VLN 指标，数据侧则是在仿真环境里做不同场景的导航数据生成与加速。做下来最关键的一个认识是：标准指标判定“到达”成功，不等于任务成功——例如智能体停在了目标点，但停止时的朝向不对，下游的 local manipulation 就无法接续。

  • 从下游任务倒推出标准 benchmark 里没有的判据，再补进评测口径
  • 长程流水线任务的真正难点，是阶段之间的隐性交接条件需要被显式度量
  • 仿真程序化生成可以降低直接样本泄露风险，也便于按场景、模板与 seed 隔离评测分布
Case B · Release Gate

自动驾驶感知：端侧资源约束下的质量收口与准出

在感知系统团队，我负责感知的发版管理、性能优化与准出。工作重心不是单个算法的效果归属，而是让多个模块在有限端侧资源里稳定完成部署、集成、发版：模型部署框架、资源预算、性能画像、端侧数据通路优化，以及跨模块的质量收口。

  • 把用户体验、算法效果、pipeline 延迟、资源占用和发版风险组织进同一套全局约束
  • 提供部署、性能分析和准出工具，让算法团队在明确的 contract 内迭代
  • 准出是一套工业级的机制问题，不是发版前的一次性检查
Case C · Roboharness

把验收做成可以无人值守连续跑的证据流水线

真实项目里，agent 能改代码、调参数、跑仿真，但长程任务会卡在“它不知道自己改完后是否真的变好”。Roboharness 把验收做成 metric 加 visual evidence 的双轨流水线，每一轮都给出 PASS / FAIL / surface-to-human 的判断依据，CI 自动出报告。

  • 机器人抓取规划从 16 秒优化到约 3 秒
  • 先用视觉发现 unknown unknown，再把它沉淀成稳定 metric
  • artifact 与 report 留痕，人不必每轮盯屏验收

Case D · Team 0 to 1

从零组建一个 9 人的系统团队

感知系统团队是我从零搭起来的，最后到 9 人规模。早期团队的难点不在招人，在于把职责边界、协作 contract 和质量标准先立住：让团队的产出对研发决策真的有影响力，而不是被当成发版前的验收工位。

  • 早期定标准的窗口期很短，标准立得晚就再也插不进去
  • 成员画像与梯队要按“定指标、建平台、管数据质量”分层配置
  • 团队价值要靠“建议被采纳后的效果回溯”来证明，而不是靠出报告的数量
03 / Team Fit

和端侧大模型团队的连接点

Scope 01

部署后一致性评测

同一份权重跨芯片、跨量化方案、跨推理框架的能力一致性验证，以及延迟、内存、功耗进入评测口径后的门禁设计。

Scope 02

全生命周期评测流水线

预训练、SFT、对齐各阶段需要不同形态的评测：轻量探针、日常回归、里程碑全量、发版评审套件，用同一套基础设施分层承载。

Scope 03

具身与 Agent 的指标设计

长程任务的阶段交接条件、工具调用正确性、任务耗时与交互次数、可靠性而非单次运气，都需要进入同一套可复现的 report。

Scope 04

语音与全双工交互评测

语音质量与识别准确率之外，真正难评的是交互行为：该打断时是否打断、误触发率、被打断后能否接续。已有全双工 benchmark 开始覆盖 turn-taking，但真实场景中的统一评测口径仍不成熟。

Scope 05

客户 POC 与交付验收

手机、座舱这类客户侧验收有自己的一套语言。我此前在整车行业做量产准出，理解甲方在验收时到底看什么、卡什么。

Scope 06

评测团队自身的产能

评测是典型的长程低频保养型工作，很适合交给 routine 化的 agent 承载。让评测团队自己先用上 AI coding 工作流，是成本、效率与准确度三角里最容易被忽略的一条边。

04 / Discussion Anchors

适合进一步展开的技术议题

Anchor 01

能力密度叙事的度量学地基

要论证能力密度随时间提升，先要回答分子怎么定义、分母怎么归一、不同代际之间如何保持可比。这套度量做扎实了，它就是技术叙事的支撑而不只是宣传口径。

Anchor 02

评测的四类受众如何分层

内部迭代信号、开源社区可信度、客户 POC 验收、对外榜单，这四类对评测的要求并不一致，甚至互相拉扯。分层承载比试图用一套指标同时满足四方更现实。

Anchor 03

跨芯片、跨量化的一致性门禁

端侧适配越多，权重与交付物之间的偏差面就越大。哪些退化可接受、哪些必须卡住，需要一套明确阈值和自动化验证，而不是靠集成期人工发现。

Anchor 04

长程任务的阶段交接条件

流水线式任务里，上一阶段“达标”常常不等于下一阶段“可用”。停止朝向这类隐性前置条件如何被识别、被度量、被写进评测集，是具身与 Agent 评测的共同难点。

Anchor 05

评测集的换血与防泄露机制

基准饱和与测试集泄露是必然发生的事。真正要设计的是私有集隔离、程序化生成、时间切片和定期退役补充的常态机制，而不是一次性的去重检查。
