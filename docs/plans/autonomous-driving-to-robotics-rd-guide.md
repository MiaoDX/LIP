## 产品定义与开篇

这份指南从自驾研发者熟悉的工作开始：定义任务边界，组织传感器和状态，生成并执行动作，收集数据，用回放、仿真和测试判断系统是否完成目标。进入机器人研发后，这些方法仍能帮助组织工作；需要重新理解的是本体、操作对象、接触、动作语义，以及任务如何复位和验收。

例如，一个做规控的工程师接到“双臂交接物体”的任务，首先要明确的是：目标怎样描述、两臂状态怎样观测、策略输出关节位置还是末端位姿、谁负责轨迹跟踪、失败怎样判断。ACT、cuRobo、MuJoCo 等工具在这些问题清楚后分别进入对应位置。这个开篇例子用于说明研发流程，不代表已完成该任务的实验。

第一版回答四个问题：

1. 我在自驾研发中已有的知识和工作方法，哪些可以继续使用？
2. 从车辆到不同机器人本体，哪些系统假设、接口和评测条件必须改变？
3. 我应怎样用公开工具完成第一项机器人研发任务，交出什么可检查的产物？
4. 从离线、仿真到真机和持续运行，每一步还缺什么证据？

以“自驾从业者”而非某一类自驾架构为默认读者：模块化系统与端到端模型的研发分工并不完全相同，文中类比按职责使用，不假设所有团队有同一套栈。

## 角色入口：从熟悉的工作开始

| 自驾研发背景 | 可迁移的方法 | 机器人任务中必须补齐 | 第一项可交付工作 |
| --- | --- | --- | --- |
| 感知 / 定位 | 标定、同步、状态估计、遮挡分析、数据质量与误差诊断 | 机器人基座/关节/工具坐标、近距离操作几何、手眼关系、接触前后状态 | 一份观测与坐标说明，配一组“看到了但无法完成操作”的失败分析 |
| 规划 / 控制 | 约束、轨迹跟踪、可达性、稳定性、时延与故障分层 | 多关节运动学、末端/关节空间、夹爪、接触、双臂协同；涉及人形时再补全身控制 | 一份动作与控制接口说明，以及固定仿真任务的执行轨迹 |
| 数据 | 采集与回放、数据版本、质量检查、场景覆盖、训练/评测拆分 | 示教来源、episode 边界、命令与实测状态、动作对齐、本体与标定元数据 | 一份 episode 数据卡、转换记录和质量报告 |
| 模型 | 训练基础设施、基线、消融、泛化、模型版本与推理优化 | action schema、归一化、chunk/horizon、闭环反馈、跨本体适配 | 固定环境和数据的基线报告，包含 checkpoint、成功率与时延 |
| 测试 / 评测 | 场景回归、故障注入、分层验收、SIL/HIL、结果追溯 | 接触与复位、任务阶段、人工介入、初始状态分布、失败恢复 | 一份任务验收定义、失败分类与可回放证据包 |
| 平台 / 系统 | 部署、资源预算、日志/trace、进程边界、超时与版本管理 | 多频率执行、机器人 SDK/ROS/控制器边界、动作时效、reset 后状态一致性 | 一张执行链路图及端到端时序、资源与故障处理记录 |

每类入口都使用同一写法：**熟悉的研发问题 → 机器人中的变化 → 可迁移/需改造的做法 → 公开参考 → 最小实验 → 交付物与停止条件**。角色入口放在前面，并在各章持续出现。

## 系统差异：类比到哪里需要停下来

下表是本文的工程分析框架，不是关于全部自驾或机器人系统的统一结论。具体取舍需要回到任务、本体和所用实现验证。

| 熟悉的出发点 | 机器人侧要重新确认的问题 | 不宜直接沿用的假设 |
| --- | --- | --- |
| ODD、功能需求与场景边界 | 机器人、工具、物体、环境、人员、任务步骤和允许介入方式 | 有一个自然语言指令就等于定义好了任务与验收条件 |
| 车辆、传感器和执行接口 | 底盘、机械臂、夹爪、力/触觉、工具坐标及控制模式 | “动作向量维度一致”就代表动作语义一致 |
| 轨迹规划与跟踪 | 关节限位、IK、碰撞、接触过程，以及策略/控制器各负责哪一层 | 一条几何无碰轨迹就足以证明抓取、插接等任务可完成 |
| 车端日志、片段与回放 | episode 的复位、观测历史、示教命令、执行结果和接触状态 | 原始动作在不同初始状态下回放仍然代表同一个闭环实验 |
| 仿真场景与 SIL/HIL | 物理步、控制步、推理等待、传感器采样和接触参数 | 流程可以运行，或画面相似，就能推出真实接触与执行时序可信 |
| 离线指标与闭环回归 | 操作成功条件、成功数/总数、介入次数、超时、复位和恢复 | loss 下降、动作预测准确或进程返回成功，就等于任务完成 |
| 软件发布与运行监控 | 现场标定、工具/物体变化、维护、保护停机和恢复流程 | 单次演示或真机链路打通，就足以证明长期稳定交付 |

机器人类型也要区分。移动导航更容易复用定位、地图和路径规划经验；机械臂操作突出运动学、接触与工具；移动操作把底盘与操作状态连接起来；足式和人形还涉及平衡、全身控制与不同的失效后果。第一版用操作任务贯穿实验，其他类型保留明确的专题入口，不把单个双臂任务的经验外推到所有机器人。

## 核心目录：沿研发流程展开

### 一、接到机器人任务，先怎样定义问题

从熟悉的需求分析和场景边界开始，把“机器人会做某件事”写成可执行、可测试的任务。明确本体、工具、对象、初始条件、观测、允许动作、成功/失败、人工介入与复位。

区分移动导航、操作、移动操作和人形任务。在共同骨架“任务 → 规划/策略 → 动作适配 → 控制器 → 执行器 → 反馈”中标出各模块职责；具体系统可以合并部分模块，但责任仍需可解释。

**产物**：任务卡、系统边界图与角色分工。先回答任务，再借助 B 文档的技术地图定位相关研究。

### 二、从车端感知与定位，到可操作的机器人状态

从标定、坐标、同步与状态估计进入，讨论相机、深度、编码器、IMU、力/扭矩等观测如何支持具体操作。重点补齐机器人基座、关节链、末端与物体的关系，以及遮挡、近距离误差和接触带来的观测变化。

几何表示、学习感知和 VLM 可以承担不同职责；能识别物体名称并不自动给出可用抓取位姿。对照仿真真值、估计量和实际部署可用观测，防止评测依赖真机拿不到的信息。

**产物**：坐标/标定说明、观测契约、时间对齐图和任务相关失败样本。几何与状态估计专题的一手资料仍需补研，不把现有 VLA 台账当作已覆盖全部感知问题。

### 三、从规控链路，到规划器、学习策略与机器人控制器

从轨迹约束和控制反馈出发，解释关节空间/末端空间、绝对值/增量、姿态表示、夹爪、频率和命令有效期。把任务规划、运动规划、策略与低层控制分别放回执行链。

用 ACT 的动作块理解预测时域、执行时域和反馈更新；用 cuRobo 或 MoveIt 2 的资料理解 IK、碰撞和运动生成。根据任务选择经典、学习或混合路线，规划器不作为 ACT 实验的必装组件。接触丰富任务与全身控制另有约束，不用简单路径规划代替这些问题。

**产物**：动作契约、控制边界、时序预算和一次可解释的执行记录。

### 四、从数据闭环，到示教、训练与本体适配

把数据来源、回放、版本和场景覆盖经验迁移到机器人 episode。重点区分观测、估计状态、下发命令、实际执行与重定向数据；记录同步、归一化、本体、标定和数据转换造成的信息损失。

ALOHA 用于讨论采集系统与策略共同设计；UMI 用于讨论 SLAM、动作表示和时延；DROID 用于讨论场景多样性、标定和数据组织。研究训练配方之前，先证明数据能被正确解释。

ACT、Diffusion Policy、VLA 和 WAM 在这里作为不同建模选择进入；比较它们对数据、动作接口、训练与推理的要求。完整演进、论文和项目列表交由 B 文档展开。

**产物**：数据卡、源数据到训练样本的转换说明、固定基线与评测拆分。

### 五、从场景回归与 SIL/HIL，到机器人闭环证据

沿用分层验证的思路，分别判断离线数据、仿真运行、策略闭环、硬件接口和真实任务。固定环境、模型、控制器、seed、复位与成功判定，区分物理步、控制周期和 wall-clock 推理时间。

失败归因覆盖数据、观测、动作适配、策略、控制器、物理环境、基础设施与评测器。保留视频和状态轨迹，并说明哪些故障不能仅凭视频判断。跨仿真器比较先对齐任务和语义，不按一次成功率给仿真器排名。

**产物**：验收条件、回归结果、失败分类和证据包；明确尚不能证明的真机结论。

### 六、从模型部署，到持续运行的机器人能力

从板端资源、服务时延和运行监控进入，说明动作时效、队列、超时、重试、取消、复位及控制器责任。把模型推理完成、控制器接受命令和实际动作分开记录。

用 openpi、Helix 和 Isaac 的公开材料理解不同部署切分，不直接把公司演示当成生产默认配置。再讨论仿真到受控真机的验证增量、现场标定与恢复；本轮不执行真机操作。

**产物**：部署与执行链图、日志/版本记录、资源与时延报告，以及从当前证据进入下一阶段还需验证的事项。

### 七、从自己的岗位选一个切入点

回到前面的六类研发角色。每个人选择一个窄任务，明确输入依赖、自己的交付物、上下游如何验收和什么时候停止扩展。读者不必先掌握所有模型路线，才能在数据质量、动作接口或评测上做出贡献。

开放任务、Agent/Skill、VLN、全身控制、灵巧操作等保留为后续专题。是否引入它们取决于任务需求，不作为所有读者的必修链条。

## 外部来源与真实经验怎样使用

事实、仓库提交、硬件、许可证和复现状态共用 [证据台账](autonomous-driving-to-robotics-guide-evidence.md)，不在 A/B 分别维护两套结论。[技术河流图](autonomous-driving-to-robotics-map-river-v2.svg) 作为共同参考，帮助把研发问题定位到研究和工具分支。A 中的自驾类比属于本文解释，不能仅凭引用某篇机器人论文就升级为“已验证的迁移最佳实践”。

| 研发问题 | 已有公开入口 | 需要继续补齐的证据 |
| --- | --- | --- |
| 观测、动作与执行 | MuJoCo、ROS 2/MoveIt 2、cuRobo、ACT/openpi | 各任务的坐标、模式、控制与实测时序 |
| 示教与数据工程 | ALOHA、UMI、DROID、LeRobot、Open X | 一个固定样例的读取、转换与质量检查记录 |
| 模型、仿真与评测 | ACT、Diffusion Policy、LIBERO、Isaac Lab、ManiSkill | 本机基线与失败样本，不能只引用上游成绩 |
| 持续运行 | openpi、Helix、NVIDIA 工程材料 | 本体相关的运行记录、恢复与真机验证；公司材料不能替代这些证据 |
| 感知、定位、接触与导航专题 | 早期目录已保留研究问题 | 专门的一手来源与实验尚不齐全，后续单独补研 |

历史版本中保留的 Soma 时间尺度、RoboClaws/RoboHarness 验收、公开基线到自有本体的经历，可作为跨模块案例候选。工厂任务交付与 VLN 数据/部署经验也保留候选位置，具体数字、职责和可披露范围在采用前重新核对 [公开时间线](../../share/work-timeline-script.md)。本轮不恢复旧文档中的业绩数字、不读取私有材料，也不把个人项目写成行业标准。

## 范围、完成标准与后续讨论

本轮交付到可对比的主文档草案：恢复自驾研发视角、明确角色入口和章节产物、共享已有事实资料。当前位于 `docs/plans/`，不新增正式正文、导航或 HTML；机器人训练和真机实验留待后续。

后续若写正文，A 的候选路径为 `drafts/autonomous-driving-to-robotics-rd.md`；B 使用自己的候选路径，避免覆盖。正式发布形态在比较后决定。

A 的内容完成标准：

- 六类读者在开篇就能找到熟悉的研发问题与第一份产物。
- 每个核心章节都明确可迁移的方法、必须改变的假设、参考材料与验证方式。
- 从任务到数据、模型、仿真、部署的闭环保持连续，不变成术语对应表。
- 一个固定实验产生角色可分工的产物；未复跑部分如实标注。
- 机器人类型与任务范围明确，车辆与机器人之间的类比不越过证据边界。
- 与 B 的核心目录和阅读目标有实质区别，事实和实验状态保持一致。
