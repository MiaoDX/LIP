# 从量产交付到机器人智能：Work Timeline 讲稿

缪东旭｜2026.07

配套演示：[面向具身智能，建设可交付、可验收的复杂系统](/share/work-timeline.html)

## 01｜开场：我这几年在做什么

我想用这几页材料，比较快地介绍一下过去七年多做过的事情。

我会沿着一条主线来讲：我的责任范围是怎么从算法工程和现场交付，逐步扩大到系统架构、团队建设、机器人完整任务，以及现在的 Agent 系统。

这几次变化看起来跨度比较大，但对我来说其实是同一条路线。我一直希望把自己的 scope 做得更大一些，不把自己长期放在一个很窄的技术点上。横向扩展的同时，系统架构和算法工程一直是我的技术支点。这部分我做得比较深，也做出过很好的结果。有这个支点以后，我才有能力继续往外走。

这一页先把三个阶段放在一起。前面是自动驾驶，中间是机器人交付和数据评测，最近是在做机器人 Agent。下一页我把这几段经历为什么能够连起来讲一下。后面每段经历都按同一个顺序展开：为什么需要做、我负责什么、我改变了什么、结果有什么证据，以及哪些能力被带到了下一阶段。

## 02｜全景：岗位在变，解决问题的方法没有变

我第一次真正理解“交付”是在 DeepMotion。2019 年到 2021 年，我在 DeepMotion 期间，负责上汽合作项目的现场交付一年多。那时候很直接：算法指标好只是起点，到了现场还要能运行，出了问题要能定位，最后客户能够验收，事情才算做完。

2021 年进入小米以后，问题变了。以前主要是我自己把一个项目交付好，后来要解决的是多个算法团队、多个平台和车型共同面对的问题。所以我的责任开始从个人交付扩大到团队建设和系统工程。

2025 年我转到机器人，先做工厂场景的集成交付，后来进入数据生产、模型部署和自动化评测。2026 年又继续往开放任务走，开始做抓取、机器人大脑和 Agent 的验收系统。

这条路线里，具体业务一直在变化，但我的工作方式比较稳定。先把问题的范围和结果定义清楚，再建立观测和证据；问题解决以后，不停在一次性的结果上，而是把它变成工具、流程或者团队能力，让它可以继续运行。

从我个人的职业选择来说，我比较像一个 T 型的人。纵向上，系统架构和算法工程是我做得最深的地方；横向上，我一直在主动扩大自己理解和负责的范围。我不追求什么事情都亲自做，但希望自己能够听懂不同方向的技术判断，找到完整系统真正卡住的地方，再把合适的人和能力组织起来。

下面我先从进入小米汽车以后，怎么从零搭建感知系统团队讲起。

## 03｜从 0 到 1：搭建感知系统团队

刚进入小米的时候，感知算法团队很多，大家都在做自己的模型和功能，但板端集成、平台迁移、发版、性能和排障这些共性工作，分散在各个团队里。很多事情依赖少数熟悉全链路的人，每换一个平台或者车型，就要重新建立一遍上下文。

我当时把这些共性问题集中起来，从零组建感知系统团队。团队最多 9 人，我负责招聘、培养、绩效和团队目标，技术上也一直在一线。我们和各个算法团队分工，把大家都会遇到的系统问题做成统一能力。

我们统一了代码组织和运行框架，让同一套代码支持多个平台和车型；也把发版、回放验证、代码检查、性能分析和 Crash 排查逐步做成自动化工具。目标很简单：同一类问题尽量只解决一次，后面的人可以直接使用结果。

这套系统建立以后，新成员通常一两天就可以提交第一个有效修改，静态检查覆盖率做到了 95%。小团队也可以同时支撑多个平台、车型和算法团队，而不是每增加一条业务线就增加一套工程。

我在带团队时比较看重两件事。第一是每个人要有清楚、完整的责任范围，不只是接零散任务；第二是团队不能长期依赖我本人。后来组织调整以后，多位成员继续承担负责人或者关键角色，我转岗以后，这些代码、工具和流程也还在继续使用。我会把这个看成团队真正建立起来的一个标志。

团队搭起来以后，下一个问题就不再是从零建设，而是业务规模变大以后，质量和性能怎么不跟着失控。

## 04｜从 1 到 N：让质量和性能可以持续运营

到了后面的量产阶段，感知已经是百人级协作，模块持续合入，也要运行在不同算力的平台上。这时候靠几个人发版前集中检查，或者出了问题再救火，已经不可能覆盖整个系统。

我主要推动了三类事情。

第一是把测试往前移。代码变更和日常版本都自动进入 SIL、DIL 和运行时检查，尽量在进入发版分支以前发现问题。

第二是把 Crash 排查里原来依赖人工经验的部分写进系统。车端数据回来以后，云端自动分析堆栈，找到对应模块和负责人，再把问题分发出去。新的判断继续沉淀成规则。

第三是把性能优化从单个热点扩大到整机资源治理。我们统一看帧率、时延、CPU、GPU 和内存，再根据不同平台的算力决定模型规格、任务调度和功能覆盖，而不是只看某一个模块是不是更快了。

最后，版本平均 Crash 率下降了大约 98%，平均定位和找到责任人的时间从一天左右缩短到一小时以内；低配平台用不到五分之一的算力，覆盖了大约 80% 的功能模块。

对我来说，更重要的不是这几个数字本身，而是它从专项治理变成了日常运行的机制。我转到机器人团队以后，这套流程仍然在继续使用。

## 05｜转到机器人：先找到支点，再进入完整任务

2025 年，我从感知系统团队负责人转到机器人团队，重新回到高级 IC 的角色。这个变化是我主动愿意尝试的，因为我希望进入机器人和具身智能，而不是一直停留在自动驾驶感知系统这一层。

刚转过去的时候，我当然不可能马上熟悉定位、地图、导航、运控和操作的所有细节。所以我没有等自己把所有机器人知识都补齐才开始做事，而是先从已经做得比较熟的系统集成、性能和测试切入。大约两三周以后，我就开始承担整体集成和性能交付。

当时我的工作有两个方向。横向上，我负责三类机器人工作站共同面对的整机集成、资源观测和性能问题；纵向上，我端到端负责其中一个螺柱工站，对任务效果、版本节奏和最终交付负责。

我们先把完整任务拆成 90 多项专项测试，覆盖定位、地图、导航等 7 类能力；再解决整机 CPU 长时间打满、无法稳定测试的问题，把 P90 控制到 60% 以下；稳定以后，三类工站分别做了 300 多组端到端自测，再移交测试团队持续运营。

我直接负责的工站，平均单次任务从 3.5 分钟降到了 2 分钟以内，也连续完成了几个版本的交付。

这段经历对我很重要，也比较能说明我进入新领域的方式。我会先找到自己能够做出结果的支点，和领域专家一起解决问题，再逐步把理解和责任扩大到完整任务。

## 06｜数据与评测：让算法迭代变得更快

机器人交付以后，我又往数据生产、模型部署和评测走了一步。

我们把原来本地单实例的数据生产，扩展到云端百实例级并行，单实例吞吐也提升了大约两倍。评测不再只看一个总分，而是把自动指标、视觉结果、人工质检和失败案例放在一起，判断下一轮到底应该补数据、改模型，还是先解决环境和基础设施问题。

我自己做算法研发有一个感受：方向还在探索期的时候，核心算法和路线判断最重要；当方案相对成熟以后，数据质量、评测方法和迭代速度会越来越重要。关键是团队能不能很快完成一轮实验，而且真的知道结果有没有变好。

现在有了 AI Coding，补工具、搭流程和做自动化都比以前容易很多。数据处理、实验执行、结果分析和日常验证，能自动跑的就应该尽量自动跑，让算法和领域专家把时间用在新的问题上。

## 07｜机器人 Agent：执行和验收要一起成立

最近一段时间，我主要在做开放场景抓取、机器人大脑和 Agent 系统。

抓取是我们进入开放场景以后先补的一项底层能力。因为周期比较短、目标范围也相对明确，第一阶段没有追求一个覆盖所有物体的最终方案，而是用检测、6D 位姿和 cuRobo 先把完整链路跑通。大约一个半月完成初版，在宇树 G1 和 RealMan 两种机器人上验证，限定范围内成功率超过 90%。

这个结果证明的是底层动作能力，不等于开放任务已经全部解决。任务再往前走，就会出现“帮我拿瓶水”或者“把房间收拾一下”这样的目标。固定 Workflow 很难覆盖这些表达，但机器人真正执行时又不能完全放开。

所以我提出并主导了 RoboClaws。上层 Agent 负责理解目标、规划和选择 Skill，Skill 里承载相对完整的任务策略，MCP 只向上暴露稳定、受控、可以观察的机器人能力。这样既保留 Agent 处理开放目标的灵活性，也不把底层物理执行变成不可控的黑盒。

另一个项目是 RoboHarness。现在研发 Agent 已经可以长时间改代码、跑仿真和调参数，新的问题是：它怎么知道自己真的做成了？如果每一轮都等人来检查，人的验收会变成下一个瓶颈。

RoboHarness 做的事情，是在任务开始前就把完成条件、失败边界、基线和证据格式定义清楚。任务运行以后，系统自动收集指标、图像、告警以及和基线的对比，最后形成一份可以复查的结果。这个项目后来拿到了部门 Hackathon 一等奖。

这两个项目其实是一对：RoboClaws 解决 Agent 怎么安全地执行，RoboHarness 解决 Agent 怎么判断自己有没有做成。除此以外，我也参与团队共建的 Executor 平台，补充机器人入口和可恢复 Workflow；最近基于这个平台完成了两组机器人任务的模型复现、训练工程优化和任务适配，并在智元 G2 上完成真机验证。

我现在比较关注的，不只是怎么用 AI Coding 多写一些代码，而是它会怎样改变研发系统。重复的实现和验证逐渐交给 Agent 以后，人的工作会更多转向定义问题、做技术判断、设计验收，以及处理还没有被自动化的新问题。

## 08｜收尾：我下一步希望做什么

如果把前面这些经历放在一起，我比较擅长的是把单点技术放进完整系统里，找到真正影响交付的问题，再通过架构、工具、评测和团队把它持续解决。

我做事情通常有四步。先说清楚系统边界和什么叫做成；再建立观测，让指标、回放、仿真和真机结果能够回答问题在哪里；问题解决以后，把方法写进工具和流程；最后交给团队或者 Agent，让它不再依赖少数关键的人。

我下一步还是希望留在机器人和具身智能方向，继续扩大自己的责任范围。系统架构和算法工程会继续是我的技术支点，同时我也希望承担团队建设、技术方向和完整交付，而不是只负责其中一个很窄的模块。

我先讲到这里。前面这些经历里，哪一段和你们现在面对的问题比较接近？我们可以直接回到那一页继续聊。
